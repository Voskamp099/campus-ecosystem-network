这个站是怎么搭起来的

15 个页面、一个可选的静态演示形态、一套带审核的后台。下面这份图不写代码， 只讲三件事：页面之间怎么连、 一个用户从进门到办完事会经过什么、 以及 背后由谁在干活。

页面地图

一次完整旅程

从一个陌生人第一次打开这个站，到一件事真正办完，中间发生了什么。 蓝色数字是步骤，深色小字说明当时是谁在操作。

打开首页

操作者：访客 · 页面：index.html
  • 首屏是一句定位语 + 一个「注册加入联盟」按钮，右侧是展示位
  • 往下滚能看到合作伙伴、权益分类、实习岗位、近期活动
  • 右下角有一个悬浮的 EN / 中文 切换按钮，中文是默认

进名录，挑一个合作方

操作者：访客 · 页面：directory.html
  • 名录分高校、企业两类，可筛选
  • 可以按机构名、方向、关键词搜
  • 选中某个合作方后 → "发起对接"

填表提交对接申请

操作者：访客（可以还没注册） · 页面：directory-apply.html
  • 填合作目标、联系人、单位、手机号、微信号
  • 提交后系统生成一个 查询编号，页面立刻显示
  • 提交走的是公开接口 /api/public/directory-applications，不要求登录

随时回来查进度

操作者：访客 · 页面：directory-status.html
  • 凭「编号 + 联系方式」查，不需要注册
  • 每一步都有说明文案，比如"正在做基础信息核验与方向初筛"
  • 在登录状态下提交会顺带绑定到账号，之后在个人中心能看到同一份记录；游客提交的记录不带账号，只能靠编号查

管理员接单并推进

操作者：管理员 · 页面：admin.html
  • 后台「对接申请」页签看到新申请
  • 推进状态：pending → reviewing → matched → contacted → completed
  • 每一步操作写入 admin_logs，谁改的、什么时候、从哪个 IP

注册账号，发布自己的内容

操作者：注册用户 · 页面：register.html → my.html → publish.html
  • 注册只需邮箱 + 密码，昵称等资料可以之后补
  • 发布活动或实习实践，状态是 pending
  • 没有后端时（静态演示形态），内容存在访客自己的浏览器里

审核通过，内容公开

操作者：管理员 → 所有人
  • 后台「用户活动」「用户实习」页签审核，通过或拒绝，拒绝可以附原因
  • 通过的内容出现在首页的"近期活动"/"实习实践"区块
  • 拒绝原因会被记录并由接口返回，但个人中心目前只显示「已拒绝」，还没把原因渲染出来

站内投递与报名

操作者：注册用户 · 页面：categories.html / 首页 · my.html
  • 接口已经就绪，但前台目前跳的是外部表单，站内这条写入链路还没接通
  • 管理员在后台仍能看到全部报名与投递记录

背后发生什么

从上到下四层。越往下越"重"，越往上越贴近人。

① 浏览器

访客 / 用户 / 管理员
页面本身：15 个 HTML 文件 + 一堆 CSS 和 JS，浏览器拿到就直接画出来，不需要先跟服务器打招呼。 前端脚本负责三件事——画内容、管登录状态、判断"现在能不能用后端"。
assets/runtime-mode.js

探测后端在不在。找不到就走"本地模式"，所有数据存浏览器里。这决定了静态演示形态能跑起来。（全站目前有三份探测实现并存，这个页面用的是其中之一。）

assets/nav-auth.js

统一管"我是谁"：登录状态、当前用户、退出。页面之间靠它共享同一份登录状态。

assets/design-tokens.css

全站配色和圆角的唯一来源。改配色只改这一个文件。

assets/brand-layer.css

把配色令牌落成看得见的品牌感：光晕、渐变标题、玻璃卡片。

② 静态资源

public/ 目录
这一层就是 public/ 目录的内容。它同时是三种部署形态的公共部分—— Node 服务把它当静态文件发出去，GitHub Pages把它整个发布成网站， 本地双击则直接从硬盘打开。

关键约束：所有资源引用必须用相对路径。写成 /assets/x.js 的话， 在子路径部署下会跳出站点根目录——而根域是用户自己的个人笔记站。

③ Node 服务

server/ · Express
routes/ 只做解析和编排，services/ 才写业务逻辑——所以同一个业务在 MySQL 和 JSON 两种存储下走的是同一条路径。
认证

JWT 放在请求头里，每个请求验一次。CSRF 用双提交 cookie。所有记录按 token 里的身份取，不认 URL 里的手机号。

审核流

用户发布 → pending → 管理员 approve/reject（可附原因）→ 通过才对外展示。

输入与安全

参数校验 + XSS 过滤 + 限流 + 安全响应头。密码 bcrypt 存储，日志里不出现哈希。

可观测

结构化日志、错误追踪、/health 健康检查、/api-docs 接口文档。

④ 存储

MySQL 为主 · JSON 兜底
主用 MySQL：共 9 张表——用户、登录日志、活动报名、投递记录、用户发布的活动、用户发布的实习、内容、后台日志、对接申请。名录卡片没有单独的表，它存在内容表里用一个分区字段区分，所以后台改名录等于改内容。
兜底 JSON：数据库连不上时，服务自动改写 data/ 目录下的 JSON 文件继续跑—— 这就是静态演示形态和本地开箱即用的底气。

邮件是可选件：邮箱验证和密码重置要用，不配就发不出信，其余功能不受影响。

三种部署形态

同一份代码，三种跑法。前端靠 runtime-mode.js 自动判断自己在哪一种形态下。

形态跑在哪后端数据存在哪适合
服务形态 Render / 自建服务器 有，完整 Express MySQL（连不上则 JSON） 正式使用
静态形态 GitHub Pages 子路径 没有 访客浏览器本地 公开演示
本地形态 双击 index.html 没有 访客浏览器本地 开发调试

怎么加一个新页面

页面是平的——都在 public/ 目录下同级，加一个文件就是加一个页面。不需要注册路由，不需要改配置。

1建文件

在 public/ 下新建一个 HTML，比如 events.html。

  1. 复制一个现有页面当骨架最快
  2. 链接一律用相对路径（events.html，不是 /events.html）
  3. 引入 assets/design-tokens.css 和 assets/brand-layer.css，配色才统一
  4. 需要登录态就引入 assets/nav-auth.js

2接进导航

新页面要能被找到，两个地方：

  1. 导航条加一个链接项（各页面都有）
  2. 如果它属于首页某个区块，加锚点 #your-id
  3. 中文文案记得同步进 i18n 对照表

3要数据的话

页面本身不存数据，数据从服务端拿。

  1. 先在 server/routes/ 定义接口
  2. 业务逻辑放 server/services/，MySQL 和 JSON 两条路都写
  3. 前端用 runtime-mode.js 判断有没有后端，有就调接口，没有就本地兜底

4中文界面 + 英文版

中文是默认，英文是可选视图。

  1. 中文文案直接写在页面里
  2. 把新文案补进 scripts/zh_inventory.json
  3. 在 scripts/build_i18n.py 的英文列表里对齐补上
  4. 跑一次脚本，它会告诉你还有哪些中文没翻译

改现有页面时，别踩这几个坑

坑为什么怎么做
资源写绝对路径 子路径部署下会跳出站点根目录 一律相对路径，或用 getAssetPath()
手改 i18n-en.js 它是生成产物，下次生成会被覆盖 改脚本，重跑脚本
在页面里定义颜色 十几个页面各写一套，早就出过一次不一致 颜色尽量写在 design-tokens.css（页面里还留有少量历史硬编码色值待收编）
把颜色写进 :root 同上，每个页面的 :root 已被清空并统一引用令牌 需要新颜色就在令牌文件里加
忘了静态形态 没有后端时接口全 404，页面直接废掉 每个新接口都要有本地兜底分支
